# 03：部署实例每日更新与进程来源的身份识别

日期：2026-10-21。状态：设计补充，尚未实施。

本文件补充 [部署单元与部署实例设计](02-deployment-units-and-instances-design.md)，细化每日更新、进程重启和服务识别策略。现有采集流程与 snapshot 定义不变；不执行远端配置读取、Redis 命令或采集器改造。

后续讨论补充：[第一期简化重启匹配与 Nexus 示例](04-simple-restart-matching-and-nexus.md) 提出按服务类型规则自动匹配、保存 INFERRED 连续性的首期方案；完整运行历史附加表可后续实施，不作为首期前置条件。

最新通用策略见 [05：通用进程识别器规则](05-generic-process-recognizer-rules.md)：核心字段一致时允许数据目录、环境变量等参数变化，不再因未分类参数变化一律转待核验，并明确人工调整优先。

## 1. 核心结论：三种身份分别管理

| 对象 | 表示什么 | 重启后的建议处理 |
|---|---|---|
| 部署单元 DU | 逻辑应用、独立服务或集群 | 逻辑身份确认未变时沿用 unit ID |
| 部署实例 DI | 某环境中的一份部署成员/部署位置 | 服务绑定仍成立时沿用 instance ID |
| 进程运行 Process Run | 某台机器上某个进程的一次运行生命期 | 观察到新的运行身份时建立新的运行记录 |

```text
部署单元 DU-001：某文件服务
  └─ 生产实例 DI-001：已登记服务部署
       ├─ 运行 PR-001：PID 1001，启动于 T1
       └─ 运行 PR-002：PID 2048，启动于 T2
```

这是“同一实例先后观察到不同运行”的示意，不表示仅凭 PID 改变就已确认服务重启。先确认部署成员匹配，再识别运行变化；PID、启动时间不能反过来承担单元或实例的永久身份。

仅凭题目中的三条命令，不能保证部署单元全局唯一，也不能确定其环境、业务系统或集群边界。平台 ID 保证管理对象自身唯一，来源绑定负责将后续观察关联到已存在对象；识别特征是匹配依据，不是业务真相的替代品。

## 2. 当前快照实际支持的证据

日常 JumpServer 快照已提供：资产 ID、IP、inspection.checkedAt、processStatus、PID/PPID、用户、name、kind、command、startedAt，以及部分进程端口/应用监听信息。

当前通用进程快照没有统一提供：boot ID、可靠的容器/命名空间身份、systemd 服务名、进程 cwd、配置文件内容、ZooKeeper myid/集群标识等。实时核验探针的部分内部记录具有 startTicks、cwd、exe、netns，不表示每日快照已经保存了这些字段。

因此，本期采用“现有字段生成候选 + 已确认的身份绑定”，不能把未来可能补充的字段默认为已有。任何额外读取/采集能力另行讨论，不作为本设计当前运行依赖。

## 3. 每日更新采用四步策略

### 3.1 固定输入与校验

1. 读取已成功完成的快照及其来源实例、版本、文件哈希、scope 和完整性。
2. 对 DevOps 使用应用/环境观察，对 JumpServer 使用每台资产自己的 checkedAt 和 processStatus；不把整批完成时间当作每条记录的新观察时间。
3. 相同批次重复导入幂等。单独同步其他来源时沿用的旧快照，不算本来源又采集了一次。
4. 旧版重导入只补历史；不覆盖已采用的较新观察。观察先后不明或来源时钟无法比较时保留候选，不能按数据库写入时间抢占当前状态。

### 3.2 先匹配已有对象

先查已登记来源绑定及身份别名，得到：

- 唯一、无冲突且满足既有规则的命中：沿用平台 ID。
- 多个目标命中，或强证据与弱特征冲突：保留 AMBIGUOUS，不取第一条。
- 没有命中：按来源创建策略处理。DevOps 的新 app ID 可创建单元；新的进程特征默认生成发现候选，先排查既有应用/服务，再确定是否建新单元。

不能因为一个进程没有匹配上，就马上再创建一个部署单元；它可能是已有服务换包、换目录、换端口或运行证据暂时不足。

### 3.3 追加观察，按字段归属更新当前投影

| 数据 | 默认来源与更新规则 |
|---|---|
| 平台 unit/instance ID | 保持不变，不从当前字段重算 |
| 领域、系统、人工说明、管理状态 | 人工维护，采集不覆盖 |
| 单元管理名称 | FOLLOW_SOURCE 时跟随确认的主来源；人工改名转 MANUAL |
| DevOps 部署 IP、声明端口、仓库、分支、配置 ID、发布步骤 | 更新 DevOps 观察；保留 branchSource/publishTimeSource，不能把推断分支当作实时运行分支 |
| PID、启动时间、进程命令、监听、CPU/内存用量 | 更新 JumpServer 运行观察；不回写成 DevOps 声明或发布事件 |
| 服务器规格 | 从对应 ECS/server-specs 观察读取，保留来源和检查时间 |
| 进程与实例、主机与实例的关联 | 单独保存匹配依据和置信度，不因 PID 被确认就自动提升应用/主机归属置信度 |

同一字段不采用“哪个来源最后写入就听谁的”。配置声明、实际监听和进程解析值可以同时存在；页面展示的有效值须带来源，不能为了合成一行而覆盖掉冲突证据。

部分采集中的缺字段不直接清空历史有效值；明确采集为空与未采集分别处理。展示保留值时同时显示其原观察时间和本轮覆盖缺口，不能以“保留最后成功值”冒充本轮已经确认。

每批先追加不可变观察，再生成变更集，最后原子发布本批采用的观察/投影。人工更新并发时检查对象 revision；失败不暴露半份导入。

### 3.4 区分属性变化与观察刷新

```text
属性相同，观察时间更新：追加观察，刷新“最后看到”，不记成一次配置变更。
分支/配置/端口等改变：沿用已匹配实例，记录配置/部署观察差异。
进程运行身份改变：沿用已匹配实例，记录新的 Process Run 与运行变化。
CPU/内存、elapsedSeconds 改变：运行观察变化，不记成发布或实例重建。
身份无法匹配：保留待确认，不以覆盖旧实例的方式消除冲突。
```

## 4. 缺失与失败如何更新

| 情形 | 建议动作 |
|---|---|
| DevOps 目标仍在，JumpServer 登录失败 | 保留部署存在证据；运行覆盖标为无法确认，显示最后成功观察时间 |
| 进程检查 partial | 已观察到且记录有效的进程可追加正向证据；不能据缺失断言其他进程退出 |
| 同一可比范围完整检查后未见已登记进程 | 记录该检查中的 NOT_OBSERVED，不宣称服务已停机或已删除 |
| 应用/部署成员未出现在完整且可比的对应来源清单 | 标记对应来源未再观察到，不级联删除 DU/DI |
| 采集失败、范围/过滤规则变化 | 不增加缺失计数、不推进删除判断；保留旧观察并展示本轮缺口 |
| 后续重新观察到 | 恢复来源 PRESENT，缺失计数清零；人工归档/禁用状态不被自动修改 |

建议初始策略：第一次有效缺失立即展示“本轮未观察到”；连续 3 次可比、成功且完整的检查都缺失时列为待核验事项。失败检查不计入，3 次也不等于连续 3 天；该阈值仅影响提示，不自动删除、停用或宣称真实停机。

应分别保存 last_seen_at、last_checked_at、missing_observation_count。last_seen_at 不因失败/缺失刷新；不同来源各自计数，不能用一次 JumpServer 缺失否定 DevOps 部署存在。仅进程观察缺失，不应将实例总体 presence 简单改成“已消失”。

## 5. 跨重启识别使用已登记的服务选择规则

### 5.1 身份判断顺序

1. 已绑定的 DevOps 应用/部署成员、原生资源或已登记逻辑服务标识。
2. 已确认的服务选择规则，例如限定资产、命名空间、配置路径/服务启动配置的本地服务绑定。
3. 现有快照中的精确路径、启动主类、部署目录、已观察监听等组合特征，只作为有范围的弱候选。
4. 进程名称、同名 jar、常用端口等仅做候选召回，不用来自动全局合并单元。

建议的本地服务识别范围：

```text
来源实例 + 稳定资产引用 + 环境上下文 + 已知命名空间范围
  + 服务种类 + 已登记的配置/部署选择规则
```

稳定资产引用优先使用 JumpServer 来源实例 + asset ID；IP 和主机名只是补充。资产重建、重新注册或跨来源归并有独立风险，不自动认为相同 IP 仍是同一台机器。

命名空间未知时记录 UNKNOWN，不填成“宿主机命名空间”。同一机器的两个容器可以出现相同路径、端口、PID；缺少隔离范围证据时不能宣称精确唯一。

命名空间是识别范围，也要区分逻辑服务范围与本次运行标识。容器 ID、netns inode 等可能随重建变化，不能不加区分地加入实例永久键；有已确认的逻辑容器服务绑定时沿该绑定定位，本次容器/命名空间值作为运行证据。网络命名空间与 PID 命名空间也不是同一个字段，现有探针的 netns 不等于已经取得 PID namespace 身份。

### 5.2 不进入永久身份键的字段

PID、PPID、startedAt、elapsedSeconds、CPU/内存、发布状态、采集时间均不进入服务永久键。Java/JDK 路径版本、依赖 jar 版本、日志参数、堆大小通常是配置/版本属性，也不应默认改变逻辑身份。

整条命令哈希可以作为“命令内容有无变化”的校验，但不能作为 unit/instance 主键。身份特征可以哈希作检索索引，同时必须保留原始特征、规则版本和依据；哈希相等不提升证据等级，也不解决不同服务共用命令的问题。

特征提取使用明确的参数/路径规则；不全局转小写、不任意删除数字、不把相对路径在未知 cwd 下补成绝对路径。命令中的脱敏值不用于区分身份，也不额外保存密码等敏感参数。

### 5.3 单元识别与本地实例识别分开

同一主机上找回某个本地服务实例后，可以沿既有 instance → unit 绑定找回部署单元。不同主机之间是否属于同一个逻辑应用/集群，则需要另外的单元归组依据。

不能用“资产 ID + 服务特征”作为部署单元的全局键：它会把同一集群的不同节点拆成不同单元。也不能只用服务名作全局键：它会把彼此独立的集群合并。

首次创建时确定本地实例绑定到已有单元还是新单元；以后沿用已保存关系，通常不必每天重新确认。规则不再满足、出现竞争候选或身份关键特征改变时才进入待核验。

## 6. 示例一：Java Jar 服务

用户提供：

```text
java -jar /home/deploy/foliday-photo-website/spa-file-http-server-0.0.1-SNAPSHOT-jar-with-dependencies.jar
```

可直接提取 launcher=java-jar、完整 jar 路径、路径所在目录、原始文件名。目录名和文件名可以提供服务候选，但不能仅据此确定业务系统、环境或已存在 DevOps 应用。

现有信息下的弱候选：

```text
资产 H1 + namespace UNKNOWN
  + launcher java-jar
  + 精确路径 /home/deploy/foliday-photo-website/spa-file-http-server-0.0.1-SNAPSHOT-jar-with-dependencies.jar
```

第一次核对后，可登记更长期的服务选择规则，示意为：

```text
绑定 DI-101 / DU-101 / 已确认环境
资产：H1
部署根目录：/home/deploy/foliday-photo-website
artifact family：spa-file-http-server（仅在此服务规则中确认）
启动方式：java -jar
其他区分条件：按实际需要登记独立配置、实例参数或监听证据
```

PID 从 1001 变成 2048，只要仍唯一满足已登记规则且无冲突，继续使用 DI-101、DU-101，新增运行观察。

包名变为新版本时，只有已有服务专属版本匹配规则或其他稳定证据支持时才自动沿用。不能对所有 jar 全局去除数字/版本后做唯一键；名称中的数字也可能区分不同服务。同目录、同 jar 同时启动多份并使用不同配置/端口时，需要继续区分实例，不能全部取第一条匹配。

因此，“去版本后的包名”适合候选与已确认规则，不是无条件唯一键；完整路径也可能被重用，须检查已有绑定和冲突。

## 7. 示例二：ZooKeeper

命令中的关键部分是：

```text
org.apache.zookeeper.server.quorum.QuorumPeerMain /conf/zoo.cfg
```

可识别为 ZooKeeper 服务进程候选，配置入口为 `/conf/zoo.cfg`。`/zookeeper-3.4.13`、JDK 路径及 classpath 中各依赖版本不应成为逻辑单元的永久身份。

本地候选范围：

```text
资产 H2 + 已知/未知 namespace 范围
  + service ZOOKEEPER
  + main class QuorumPeerMain
  + config path /conf/zoo.cfg
```

该规则可以支持找回已登记的本地实例，但命令没有给出集群 ID、节点 ID、dataDir、环境或其他成员；不能从命令推导“它属于哪个 ZooKeeper 集群”。不同容器的 `/conf/zoo.cfg` 也不是同一个文件身份。

未来如果已有或经授权补充了 `dataDir/myid`、`server.*` 等配置证据，可以辅助识别节点与 ensemble。ZooKeeper 的 myid 对应本 ensemble 的 server.x，不能单独作为全公司唯一 ID；集群成员列表也会变化，不应把整份配置哈希设为永久集群身份。[ZooKeeper 3.4.13 官方说明](https://zookeeper.apache.org/doc/r3.4.13/zookeeperAdmin.html)

建议先核对并登记一个稳定的“集群单元 ID”，各节点分别绑定环境实例。节点重启沿用单元/实例，运行记录变化；节点扩容则新增实例。没有集群归组证据时，保留未分组节点候选，不把所有 ZooKeeper 进程自动合并。

## 8. 示例三：Redis

用户提供：

```text
/usr/local/bin/redis-server 127.0.0.1:7201
```

它提供 Redis 类型和本地地址/端口线索，候选范围必须包含资产及命名空间：

```text
资产 H3 + 已知/未知 namespace 范围
  + service REDIS
  + 地址线索 127.0.0.1:7201
```

不能把 `127.0.0.1:7201` 当成全局唯一 Endpoint；不同机器/网络命名空间中的回环地址指向不同范围。7201、7202 不因都叫 redis-server 而自动合并，是否属于同一集群需要独立证据。

Redis 支持重写进程标题，标题可包含监听地址。因此这条进程文本不一定是完整原始启动参数，不能据此还原配置文件或完整监听范围；已有 appPorts/端口证据应另行核对。[Redis 官方配置示例](https://github.com/redis/redis/blob/7.2/redis.conf)

只有“同一资产 + 地址/端口”时，默认属于弱识别。已登记且本次唯一、无冲突地匹配到该本地服务，可以按策略延续既有实例，但仍标注 INFERRED，不因为连续多天相同就升级成 EXACT。若有配置路径、受管服务身份或已确认原生资源/集群节点身份，可另保存更强依据。

端口从 7201 变为 7202 时，若只有端口这个弱锚点，不能自动说是原实例改端口；可能是新服务、另一节点或重用。已有稳定服务绑定及其他证据支持时才更新原实例，并追加新的选择别名。不同服务后来重用 7201 时也不能继承旧单元的身份。

## 9. 实际匹配和防重复创建流程

```text
本次进程观察
  → 提取候选特征，保留原始证据与缺失字段
  → 查已登记的服务选择规则/身份别名
      → 唯一命中且无冲突：沿用 instance → unit
      → 多命中或矛盾：AMBIGUOUS，保留候选
      → 零命中：生成/更新发现候选
          → 检查能否归到已有 DevOps 应用、单元或已登记集群
          → 确认绑定已有对象，或确定新的逻辑服务边界后创建
  → 识别本次 Process Run
  → 追加观察并更新对应来源投影
```

首次确认保存的是“选择什么服务、属于哪个单元/环境”的可重复规则，不是只保存当时的 PID。以后常规重启自动沿用；不能识别的变化才再次核对。

首次从进程建单元时环境未知，先保留候选，不默认 PRODUCT，也不引入额外 SHARED 环境。若平台已有显式共享上下文绑定，可以在该既定关系下引用同一物理运行；不能根据调用方所在环境自行复制/归组。

自动绑定的建议门槛：唯一满足已登记规则、scope/资产/环境兼容、无矛盾证据。新弱特征即便搜索只返回一个名称相似单元，也不默认达到自动绑定门槛。匹配依据、实体身份质量、进程所有权和集群归属置信度分别保留。

## 10. 对上一版表结构的补充

### 10.1 来源观察头按来源角色区分

上一版单一 `current_observation_id` 不足以表达 DevOps 部署配置、JumpServer 运行和 ECS 规格同时有效。

本轮建议：实例当前投影采用各来源绑定的观察头；`deployment_instance_source` 增加 `latest_observation_id, latest_check_observation_id, presence_status, last_checked_at, missing_observation_count`。来源角色明确区分 DEPLOYMENT、RUNTIME、HOST_SPEC 等，观察头必须引用本实例、对应来源角色和已采用导入批次。

实例主表的 current_observation_id 如果保留，应明确仅指主要部署观察，不能被一次进程检查替换成所有字段的唯一来源。配置与运行的有效当前视图按角色组合，不做最后写入覆盖。

### 10.2 新增 `deployment_identity_alias`：服务选择规则与别名

建议字段：

```text
id
instance_id NULL             确认后绑定；unit 通过 instance 获得
source_instance_key
host_reference_json          来源实例 + 资产 ID 等稳定来源定位
namespace_key NULL           未知不假定宿主机
environment NULL             候选可以未知，绑定须有明确上下文
service_kind
selector_kind                EXACT_PATH / CONFIG_PATH / REGISTERED_SERVICE / ENDPOINT_HINT 等
selector_json                保留实际特征、参数和适用范围
fingerprint_hash             候选检索用，不是 unit/instance ID
rule_version
binding_status               CANDIDATE / BOUND / REVOKED / SUPERSEDED
confidence / basis
valid_from / valid_to NULL   规则/绑定的管理有效范围
evidence_json
created_by / created_at
```

同一实例可以有多条经过确认的别名，例如旧 jar 路径和新部署规则；新增别名不重新生成 unit/instance ID。规则升级以新版本追加，不静默改写旧观察的匹配结论。

同范围、同环境下同一活动选择标识不得同时绑定不同实例；如果实际存在多个服务，先补充区分条件。不同选择规则也可能范围重叠，运行时仍须检查多目标命中，不能认为唯一索引已证明选择规则互斥。

历史已撤销/替换规则保留，后来的端口/目录重用需要新的确认关系，不自动继承旧绑定。派生的进程特征用此表管理，不直接套用上一版“原生来源 ID 永久排他绑定”的约束；否则弱特征重用会阻止合法新绑定，或错误复用旧对象。

### 10.3 新增 `process_run`：一次进程运行

建议字段：`id, host_reference_json, namespace_key NULL, boot_id NULL, pid, started_at NULL, start_ticks NULL, first_seen_at, last_seen_at, identity_quality, identity_basis`。

若实际具备足够证据，可采用“机器身份 + 主机 boot ID + PID 命名空间范围 + PID + startTicks”识别某次运行。startTicks 是自本次系统启动以来的进程启动计数，不能跨机器/boot 单独比较。[Linux 进程字段说明](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)

现有日常快照只能退化使用资产、PID、startedAt 等，缺少 boot/namespace/时间精度证据时必须保留弱身份及可能冲突。不能假定实时探针内部字段已在日快照中提供。

不因进程一次未出现就填写确切 finished_at。last_seen_at 仅代表最后观察到的时间；相邻采集之间退出/启动边界及中间发生了多少次重启均可能未知。

### 10.4 新增 `instance_process_observation`：实例与运行的观察关系

建议字段：`id, import_run_id, catalog_observation_id, instance_id, process_run_id, identity_alias_id NULL, observed_at, match_confidence, match_basis, source_locator_json`。

允许一个实例关联多个进程，例如服务主/工作进程；也不强制一个 JVM 只能服务一个应用实例。多对多关系必须有证据，不能仅因为同机或同一 JVM 就广播绑定。

同一批、同一源进程观察、同一实例关系幂等；关系表保留每次观察，不把“上次关联过”当成本次真实运行证据。

相应扩展 catalog_observation 的 record_kind，支持来源角色明确的 RUNTIME 观察；原 DEPLOYMENT 观察继续只承载部署来源语义。若实现本轮全部进程身份与运行历史能力，则在上一版 10 张表基础上建议增加以上 3 张，合计 13 张；仍未涉及采集结构变更。

## 11. 重启、替换与扩容的区别

| 观察变化 | 可以记录 | 不可自动断言 |
|---|---|---|
| 绑定同一服务，PID/启动身份改变 | 新运行观察，可能的运行替换/重启 | 精确重启时刻、采集间只重启了一次、代码已发布 |
| PID 相同、启动身份改变 | 进程号重用或新的运行候选 | 一直是原来的运行 |
| 同一规则同时命中两份服务进程 | 并行运行/多成员候选；根据既定进程组规则进一步区分 | 旧进程已退出，或只保留列表第一项 |
| 同一单元确认增加新部署成员 | 新增实例及来源绑定 | 因名字相同而把新成员覆盖到旧实例 |
| 目录/端口变更且没有强锚点 | 身份变化候选或新服务候选 | 肯定是原实例迁移 |
| 同一集群节点重启 | 已确认节点/实例保持，运行观察变化 | 集群变成新的单元 |

日采样适合保留“观察到的运行变化”，不能提供完整重启事件账本。平台可以统计已确认/推断的变化次数并标覆盖范围，不应把它展示为绝对重启次数。

## 12. 本轮建议采用的更新策略

1. **身份保持，属性更新**：唯一满足既有身份绑定时沿用 DU/DI，追加新观察，不每日删除重建。
2. **来源分工，人工保护**：来源只更新自己负责的观察及投影，不覆盖人工分类，不混淆配置与实际运行。
3. **运行分代**：PID/启动身份变化归入 Process Run，先核验服务归属，再判断是否延续实例。
4. **绑定留存**：首次确认保存有范围的服务规则，后续通过规则/别名识别已创建对象。
5. **新进程先候选**：零命中、多个命中或矛盾都不自动新建/合并正式单元。
6. **缺失不删除**：完整可比观察才记录缺失；连续缺失仅提示核验，失败不累加，管理对象保留。
7. **不制造证据**：当前没有配置/集群/namespace 信息就明确未知，不因设计需要而补值。

后续业务仍需确认：哪些首次服务选择规则可由维护者登记、哪些来源 ID 足够稳定、集群单元的管理边界，以及弱匹配自动延续的允许范围。本轮以已登记规则内的唯一无冲突匹配为自动延续边界。

## 13. 后续实施验证场景

- 相同输入重复导入、旧版晚到、复制沿用旧快照，不产生假新观察或回滚当前状态。
- 同一绑定服务重启换 PID，DU/DI 不增加，运行记录增加；同 PID 新启动身份不被当作连续运行。
- jar 换版本：已登记服务规则内可延续，无规则时保留候选；同 jar 并行多实例不取第一项。
- 两资产或两个命名空间出现同一 Redis 回环地址，不跨范围合并；namespace 未知时保留弱身份。
- 两 ZooKeeper 使用同一配置路径，不自动归同集群；集群成员变化不导致重新生成单元 ID。
- 完整缺失、partial、失败、范围变化分别处理；DevOps 仍存在但运行无法核验时状态不互相覆盖。
- 选择规则变更、目录/端口重用、候选冲突有历史及管理边界，不静默改绑旧单元。
- 人工分类并发修改、发布前中断和重启不暴露半成品更新。

本次只新增设计记录和关联索引，未执行数据库迁移、采集或服务登录。
