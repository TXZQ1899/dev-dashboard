# Zookeeper 部署单元梳理 Task

状态：待实施；先执行候选梳理和只读核查，确认结果后写入。共同规则见 [00-共同约束](00-共同约束.md)。本任务不表示已发现实际实例或集群。

## 目标与输出

- 创建技术类型为 `Zookeeper`、单元类型建议为 `MIDDLEWARE` 的部署单元；名称为 `Zookeeper_cluster_序号`。明确独立部署同样使用此命名，并有一个节点。
- 输出候选进程清单、应用关联排除清单、拟创建单元与节点、证据和置信度、待核实项、覆盖与失败情况；环境初始为「待识别」。类型归类为设计建议，实施时须与现有目录枚举及产品口径核对。

## 专项核查和归并任务

- 从 Java 主类、启动脚本和进程参数识别 QuorumPeerMain 等服务候选；客户端、工具进程不计为服务。检查容器实例与同机多套配置。
- 定位实际生效的 zoo.cfg、动态配置及 dataDir 内 myid；记录 server.N 成员、客户端与 quorum/election 端口、配置版本及本节点 ID。配置变量、主机名解析、动态重配置及多个配置文件须区分生效与候选。
- 比对各节点有效成员配置、节点 ID、Endpoint 与可见资产；动态配置应记录版本和观察时间，必要时使用受限只读状态信息交叉核对。相同成员列表但版本冲突、节点 ID 重复或名称解析多候选时暂停归并。
- 明确 standalone 配置或经充分核实仅一个服务的独立部署才可单节点建单元；仅看到一个 quorum 成员不算独立。观察到未纳管成员时作为未解析成员列出。

## 执行步骤

1. 从已完成快照建立本类型候选，记录每台资产的采集状态、进程与直接/推断端口；评估 DevOps 关联，排除已关联项，冲突保留待核实。
2. 确认版本和部署方式，按上述专项规则定位有效配置，实施最小只读检查；分别保存观察时间、节点身份、Endpoint、证据来源与限制。
3. 汇总节点视图，识别单节点、多节点和未解析成员；给出证据与置信度，列出冲突、无法访问主机和可能的同机多实例，生成导入预览。
4. 核对预览并确认后，事务写入单元、待识别环境、实例、来源观察及变更；重复执行保持身份和序号稳定，失败回滚。
5. 验证容器运行、持久化和结果可追溯；输出覆盖范围与剩余未解决项，不将未观察到等同停机。

## 专项测试与验收

- 三节点同一 ensemble → 一个单元三个实例；两套 ensemble 共用主机 → 两个单元。
- 动态配置新旧版本冲突、myid 不一致、仅一台可登录、客户端命令被误识别 → 不误归并；明确 standalone → 单节点。

- 执行共同约束中的通用测试；检查不同证据环节置信度独立、敏感信息遮盖、较旧及不完整观察不能误更新、预览与落库一致。
- 验收时逐条核对单元名称、环境、节点、证据、未解析原因及排除原因；不可将无法证明的集群或独立部署写成确定结果。
