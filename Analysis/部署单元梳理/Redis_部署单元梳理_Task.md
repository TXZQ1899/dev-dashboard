# Redis 部署单元梳理 Task

状态：实施中；已分批核查并创建部分部署单元，其余候选仍需核实。共同规则见 [00-共同约束](00-共同约束.md)。

## 目标与输出

- 创建技术类型为 `Redis`、单元类型建议为 `DATABASE` 的部署单元；名称为 `Redis_cluster_序号`。明确独立部署同样使用此命名，并有一个节点。
- 输出候选进程清单、应用关联排除清单、拟创建单元与节点、证据和置信度、待核实项、覆盖与失败情况；环境初始为「待识别」。类型归类为设计建议，实施时须与现有目录枚举及产品口径核对。

## 专项核查和归并任务

- 识别 redis-server、容器服务与实际配置；区分 Sentinel、客户端、代理及多个同机实例，直接监听与推断端口分别保存。
- 只读核查运行模式、有效配置及必要的复制/集群成员信息；适配 standalone、主从、Sentinel 和 Redis Cluster。记录节点 ID、角色、Endpoint、复制关系、集群状态及时间；密码、认证信息不落盘。
- 主从及 Sentinel 模式按经核实的 Redis 数据服务成员关系归并；Sentinel 属于监控/协调角色，其是否作为独立部署单元先确认，不直接算数据节点。Redis Cluster 用节点 ID 与成员视图交叉确认；不同主从组不能仅因同一 Sentinel 自动合并。
- 明确单独运行且非复制/集群成员才单节点；仅从配置看不到 replica 或暂无法连接其他节点不够。

## 执行步骤

1. 从已完成快照建立本类型候选，记录每台资产的采集状态、进程与直接/推断端口；评估 DevOps 关联，排除已关联项，冲突保留待核实。
2. 确认版本和部署方式，按上述专项规则定位有效配置，实施最小只读检查；分别保存观察时间、节点身份、Endpoint、证据来源与限制。
3. 汇总节点视图，识别单节点、多节点和未解析成员；给出证据与置信度，列出冲突、无法访问主机和可能的同机多实例，生成导入预览。
4. 核对预览并确认后，事务写入单元、待识别环境、实例、来源观察及变更；重复执行保持身份和序号稳定，失败回滚。
5. 验证容器运行、持久化和结果可追溯；输出覆盖范围与剩余未解决项，不将未观察到等同停机。

## 专项测试与验收

- 一主两从的已核实复制组归一单元；两个复制组由同一 Sentinel 管理仍分开。
- Cluster 多节点、节点迁移、认证失败、不同网络地址及 standalone 均保留正确证据。

- 执行共同约束中的通用测试；检查不同证据环节置信度独立、敏感信息遮盖、较旧及不完整观察不能误更新、预览与落库一致。
- 验收时逐条核对单元名称、环境、节点、证据、未解析原因及排除原因；不可将无法证明的集群或独立部署写成确定结果。
