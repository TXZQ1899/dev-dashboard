# Elasticsearch 部署单元梳理 Task

状态：已建档 15 个 Elasticsearch 单元，并将已核实连接关系的 Kibana 归入对应单元；其余 ES 和 Kibana 候选仍待核实。共同规则见 [00-共同约束](00-共同约束.md)。

## 目标与输出

- 创建技术类型为 `Elasticsearch`、单元类型建议为 `MIDDLEWARE` 的部署单元；名称为 `Elasticsearch_cluster_序号`。明确独立部署同样使用此命名，并有一个节点。
- 输出候选进程清单、应用关联排除清单、拟创建单元与节点、证据和置信度、待核实项、覆盖与失败情况；环境初始为「待识别」。类型归类为设计建议，实施时须与现有目录枚举及产品口径核对。

## 专项核查和归并任务

- 识别 Elasticsearch 服务 Java 进程、启动参数与安装/配置路径，排除客户端与其他 Java 服务；每个节点单独核实。
- 记录有效配置中的 cluster.name、node.name、角色、HTTP/transport Endpoint、发现配置；可访问时用只读集群信息核对 cluster UUID、节点 ID 和成员视图。凭据与敏感内容不保存。
- 以运行时 cluster UUID 及节点 ID/成员视图交叉验证为主要依据；cluster.name 和相同 discovery seed 仅作候选，不能单独归并。不同版本、重建或 UUID 变化需人工复核连续性。
- 明确单节点模式且排除其他成员才单节点；无法查询集群或仅见一个进程保留未知。

## 执行步骤

1. 从已完成快照建立本类型候选，记录每台资产的采集状态、进程与直接/推断端口；评估 DevOps 关联，排除已关联项，冲突保留待核实。
2. 确认版本和部署方式，按上述专项规则定位有效配置，实施最小只读检查；分别保存观察时间、节点身份、Endpoint、证据来源与限制。
3. 汇总节点视图，识别单节点、多节点和未解析成员；给出证据与置信度，列出冲突、无法访问主机和可能的同机多实例，生成导入预览。
4. 核对预览并确认后，事务写入单元、待识别环境、实例、来源观察及变更；重复执行保持身份和序号稳定，失败回滚。
5. 验证容器运行、持久化和结果可追溯；输出覆盖范围与剩余未解决项，不将未观察到等同停机。

## 专项测试与验收

- 相同 UUID 三节点 → 单元三实例；相同 cluster.name 但 UUID 不同 → 两个单元。
- 身份冲突、HTTP 不可访问、仅配置 discovery 候选、单节点模式均正确呈现。

- 执行共同约束中的通用测试；检查不同证据环节置信度独立、敏感信息遮盖、较旧及不完整观察不能误更新、预览与落库一致。
- 验收时逐条核对单元名称、环境、节点、证据、未解析原因及排除原因；不可将无法证明的集群或独立部署写成确定结果。
