# RabbitMQ 部署单元梳理 Task

状态：本轮 11 个快照候选已核查并建档；覆盖限制见下文。共同规则见 [00-共同约束](00-共同约束.md)。

## 目标与输出

- 创建技术类型为 `RabbitMQ`、单元类型建议为 `MIDDLEWARE` 的部署单元；名称为 `RabbitMQ_cluster_序号`。明确独立部署同样使用此命名，并有一个节点。
- 输出候选进程清单、应用关联排除清单、拟创建单元与节点、证据和置信度、待核实项、覆盖与失败情况；环境初始为「待识别」。类型归类为设计建议，实施时须与现有目录枚举及产品口径核对。

## 专项核查和归并任务

- 通过 beam.smp 的 RabbitMQ 启动特征和节点配置识别主服务，排除 epmd、Erlang 辅助进程及客户端；推断监听端口不得当作直接 PID 证据。
- 读取实际配置、节点名、节点地址、启动选项；在授权下通过版本适配的只读状态或管理接口获取集群名称、节点列表和状态。Erlang cookie 是敏感凭据，不读取或记录其值。
- 以节点标识和同一时段的集群成员视图相互印证；共同 cookie、同主机、队列/连接、仅有 epmd 端口均不能证明归属。镜像队列、quorum queue 副本是队列层关系，不能替代集群成员判断。
- 明确非集群单节点才创建单节点单元；节点不可达、身份不一致或查询失败保留未解析。

## 执行步骤

1. 从已完成快照建立本类型候选，记录每台资产的采集状态、进程与直接/推断端口；评估 DevOps 关联，排除已关联项，冲突保留待核实。
2. 确认版本和部署方式，按上述专项规则定位有效配置，实施最小只读检查；分别保存观察时间、节点身份、Endpoint、证据来源与限制。
3. 汇总节点视图，识别单节点、多节点和未解析成员；给出证据与置信度，列出冲突、无法访问主机和可能的同机多实例，生成导入预览。
4. 核对预览并确认后，事务写入单元、待识别环境、实例、来源观察及变更；重复执行保持身份和序号稳定，失败回滚。
5. 验证容器运行、持久化和结果可追溯；输出覆盖范围与剩余未解决项，不将未观察到等同停机。

## 专项测试与验收

- 三节点互认 → 一个单元；两个独立节点共享 cookie 不自动合并。
- epmd 不生成实例；无权限状态查询、节点名称冲突及单节点场景均覆盖。

- 执行共同约束中的通用测试；检查不同证据环节置信度独立、敏感信息遮盖、较旧及不完整观察不能误更新、预览与落库一致。
- 验收时逐条核对单元名称、环境、节点、证据、未解析原因及排除原因；不可将无法证明的集群或独立部署写成确定结果。
