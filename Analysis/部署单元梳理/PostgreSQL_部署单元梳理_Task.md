# PostgreSQL 部署单元梳理 Task

状态：已按用户确认创建当前发现的四个部署单元；部分运行配置与复制状态仍待核实。共同规则见 [00-共同约束](00-共同约束.md)。

## 目标与输出

- 创建技术类型为 `PostgreSQL`、单元类型建议为 `DATABASE` 的部署单元；名称为 `PostgreSQL_cluster_序号`。明确独立部署同样使用此命名，并有一个节点。
- 输出候选进程清单、应用关联排除清单、拟创建单元与节点、证据和置信度、待核实项、覆盖与失败情况；环境初始为「待识别」。类型归类为设计建议，实施时须与现有目录枚举及产品口径核对。

## 专项核查和归并任务

- 按 postgres postmaster、数据目录、监听 Endpoint 和父子进程识别服务实例，排除 worker、客户端及代理；同主机不同 data directory 是不同候选。
- 只读核实版本、生效配置、数据目录、实例身份及主备关系；可用时查询系统标识、恢复状态及复制关系，记录观察时间，区分复制槽和实际成员。受管数据库或无法访问的节点作为未解析对象。
- 经证实属于同一复制/HA 编组的主备归一单元；相同 system identifier 可来自备份或克隆，需结合现行复制和管理证据，不独立证明同一活动集群。不同数据库名也不等于不同服务器实例。
- 明确无复制/HA 的独立实例为单节点；配置陈旧、无法查询或备份副本的归属不明时不推断。

## 执行步骤

1. 从已完成快照建立本类型候选，记录每台资产的采集状态、进程与直接/推断端口；评估 DevOps 关联，排除已关联项，冲突保留待核实。
2. 确认版本和部署方式，按上述专项规则定位有效配置，实施最小只读检查；分别保存观察时间、节点身份、Endpoint、证据来源与限制。
3. 汇总节点视图，识别单节点、多节点和未解析成员；给出证据与置信度，列出冲突、无法访问主机和可能的同机多实例，生成导入预览。
4. 核对预览并确认后，事务写入单元、待识别环境、实例、来源观察及变更；重复执行保持身份和序号稳定，失败回滚。
5. 验证容器运行、持久化和结果可追溯；输出覆盖范围与剩余未解决项，不将未观察到等同停机。

## 专项测试与验收

- 已核实一主一备 → 一个单元；克隆拥有同 system identifier 但未证明复制 → 不合并。
- 多 worker、同机多 data directory、复制不可见和独立实例均覆盖。

- 执行共同约束中的通用测试；检查不同证据环节置信度独立、敏感信息遮盖、较旧及不完整观察不能误更新、预览与落库一致。
- 验收时逐条核对单元名称、环境、节点、证据、未解析原因及排除原因；不可将无法证明的集群或独立部署写成确定结果。
