# 04：第一期简化重启匹配规则与 Nexus 示例

日期：2026-10-21。状态：针对本轮讨论提出的简化策略，尚未实施。

本文件细化 [进程身份识别分析](03-instance-refresh-and-process-identity.md)。现有采集和 snapshot 定义不变；第一期可以先用已有观察及来源绑定保存运行变化，不要求立即实现上一份文档中完整的 Process Run 三张附加表。

后续修订：[通用进程识别器规则](05-generic-process-recognizer-rules.md) 按用户最新指示，将数据目录及普通参数变化排除在否决条件之外，采用统一启动特征和通用匹配器。下文 Nexus 数据目录参与身份区分等策略保留为历史讨论，最新匹配规则以 05 为准。

## 1. 结论：可以简化，限定匹配范围与参数含义

用户提出的“启动命令、监听端口相同，PID 改变仍识别为同一单元”可以作为第一期自动延续规则。建议明确为：

```text
同一来源资产 + 同一环境
  + 无已知隔离范围冲突
  + 核心服务启动特征一致
  + 已观察监听匹配
  + 无身份关键参数冲突
  + 唯一命中已有实例
    => 自动沿用 instance ID，再沿既有绑定获得 unit ID
```

不要求每次重启都人工确认。类型解析规则可内置并记录版本，不要求每个常规服务都先手写专属规则。

自动匹配结果保存为 INFERRED，附输入、匹配条件和规则版本。它用于推断本地服务连续性，不作为新的全局主键，也不自动合并不同主机/环境中的逻辑单元。

已存在 DevOps/原生资源等更强来源绑定时优先使用；核心特征匹配不能覆盖已知的强身份冲突。环境或隔离范围存在多个合理候选时不自动选一条。

## 2. “启动命令相同”比较什么

比较按服务类型提取的核心特征，而不是整条命令逐字符相同，也不是只比较 java、redis-server 等可执行文件名。

| 参数类别 | 示例 | 首期处理 |
|---|---|---|
| 业务服务入口 | NexusMain、java -jar 的业务包入口 | 用来识别具体服务类型/入口 |
| 服务位置与数据/配置线索 | 部署目录、独立配置路径、karaf.data | 保留比较；变化可能影响实例身份 |
| 已识别的性能参数 | Xms、Xmx、MaxDirectMemorySize | 记录参数变化，不单独导致重建单元/实例 |
| 已识别的日志参数 | JVM 日志输出参数、日志路径 | 保存原值，通常不参与核心身份匹配 |
| 运行属性 | PID、启动时间、CPU/内存等 | 保存为观察，不进入服务匹配键 |
| 运行时/依赖版本 | JDK 路径版本、依赖 jar 版本 | 依据服务类型规则处理，不默认生成新单元 |
| 未分类或可能改变业务身份的参数 | 不明业务参数、不同配置/数据目录 | 保留差异，无法解释时不直接自动延续 |

不能一概忽略所有 -D 参数：Xmx 调整与 karaf.data 改变含义不同。规则也不全局删除数字、转小写或去除所有路径版本。

## 3. 从 Nexus 命令提取的特征

用户提供的命令中，核心线索为：

```text
服务类型候选：NEXUS
业务入口：org.sonatype.nexus.karaf.NexusMain
启动脚本声明：/usr/local/nexus/nexus-3.16.2-01/bin/nexus
安装目录候选：/usr/local/nexus/nexus-3.16.2-01
数据目录声明：../sonatype-work/nexus3
```

`com.install4j.runtime.launcher.UnixLauncher` 是启动包装入口；这里只比较它会遗漏具体业务区别，因此本例使用命令中明确出现的 NexusMain。

Sonatype 官方说明 karaf.data 是 Nexus 数据目录，相对路径按安装目录解释，而不是按 bin 目录解释。[官方说明](https://support.sonatype.com/hc/en-us/articles/218707647-How-to-Determine-the-Location-of-the-Nexus-Repository-3-Data-Directory)

由此，可以使用明确标注的 NEXUS-v1 产品规则生成词法归一化候选：

```text
数据目录候选：/usr/local/nexus/sonatype-work/nexus3
```

这是依据启动参数及产品规则生成的路径候选，保留原值和依据；没有读取文件或验证符号链接，不宣称已确认真实文件位置。该产品规则也不推广到所有 Java 服务。

本例可保存的匹配描述示意为：

```text
资产：已有 JumpServer 来源实例 + asset ID
环境：已有已确认环境
服务类型：NEXUS
业务入口：org.sonatype.nexus.karaf.NexusMain
数据目录候选：/usr/local/nexus/sonatype-work/nexus3
监听：实际采集得到的监听信息
解析规则：NEXUS-v1
```

题目中的命令没有提供监听端口，不能自行补 Nexus 默认端口。监听必须来自现有进程 ports 或 appPorts 的 PID 关联；原始命令和快照仍作为证据保存。

JVM 堆、直接内存、日志参数变化不必改变以上核心描述。安装目录版本变化时，如果产品规则得到相同数据目录且其他条件满足，可以按本规则继续匹配；不能仅凭 NexusMain 相同就忽略不同数据目录。

## 4. 监听匹配的简单边界

- 在同一来源资产、同一环境内比较；不同资产相同端口不合并。
- 有绑定地址、端口、协议时保留完整 Endpoint；只有端口时按较弱证据处理，不补 TCP。
- 去重并排序后比较监听描述，避免数组顺序变化导致误判。
- 没有监听数据不等于观察到零监听，也不算“端口相同”。不凭声明端口回退值满足实际监听条件。
- 已有明确主服务端口规则时，可比较主服务 Endpoint，将辅助端口变化作为属性；没有角色规则时先比较已有监听集合，变化保留待确认。
- 命名空间未知时不能填成宿主机范围；在现有资产范围唯一、无冲突命中可以按首期弱规则延续，仍为 INFERRED。出现容器/隔离范围冲突或多候选则停止自动匹配。

这允许第一期利用已有数据工作，也明确保留了未采集隔离信息的限制。

## 5. 变化如何处理

| 本次观察 | 首期建议 |
|---|---|
| 核心服务、范围、监听匹配，PID 改变 | 自动复用 DI/DU，追加运行观察 |
| 上述条件满足，Xmx 从 1200M 改成 2G | 自动复用，并记录性能参数差异 |
| JDK/依赖版本变化，但服务核心描述按产品规则不变 | 其他条件满足时可复用，记录版本变化 |
| 相同 NexusMain，但数据目录不同 | 不直接认作同一本地实例；保留候选或匹配另一个已有实例 |
| 端口变化且没有其他已确认身份依据 | 转入待确认，不马上创建新单元 |
| 监听未采到、检查 partial/failed | 不能声称满足监听匹配；保留已有对象和本轮覆盖缺口 |
| 同一规则命中多个已有实例/多份进程 | 保留歧义，不取第一条，也不覆盖另一份实例 |
| 强来源身份不同，即使核心命令和端口一样 | 不按弱规则自动归并 |

只要匹配到原实例，就直接沿 instance → unit 找回单元，无需每天重新判断集群/系统归属。PID、启动时间变化记录为“观察到运行变化”；是否确实重启、期间重启几次仍不由每日快照完整证明。

同样的规则没有命中，不等于应新建单元。零命中时先查已有同类服务与历史绑定，保留换端口/换配置/新服务等候选，避免识别失败造成重复创建。

## 6. 第一期最小保存内容

沿用上一版 catalog_observation、deployment_instance_source 等结构即可先保存：

```text
unit ID / instance ID
来源资产、环境和已知隔离范围
服务特征 JSON + 解析规则版本
实际监听证据与本次 PID/启动时间
来源版本、记录位置、观察时间
匹配结果 INFERRED 与匹配依据
参数差异/未解释冲突
```

特征哈希仅用于快速查候选；不以它替换平台 ID。旧特征、原始观察及历史绑定保留，可在以后增加身份别名和完整运行历史时继续使用。

本文件是对第一期复杂度的收敛：先实现有范围、可解释的自动匹配和观察更新，再按实际需求扩展完整的运行生命周期表。没有新增必须的远端采集字段或宿主机依赖。

## 7. 分析结论

可以接受用户提出的简化方向，前提是把“相同启动命令”定义为具体服务的核心特征，并补充来源资产、环境、监听证据、唯一候选和冲突检查。

Nexus 示例中，PID、JVM 内存和日志参数变化可以不改变单元/实例；NexusMain、数据/配置范围及实际监听用于识别连续性。普通重启自动延续，无需每次人工确认；不同数据范围、缺失监听和多候选才进入待核验。

本次仅记录设计建议，未改采集、快照、匹配代码或数据库。
