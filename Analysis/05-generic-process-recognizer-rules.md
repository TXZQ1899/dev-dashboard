# 05：通用进程识别器规则

日期：2026-10-21。状态：按本轮选择固化规则，尚未进入代码实现。

现有采集、snapshot 定义及页面逻辑保持不变。本文件是 [简化重启识别分析](04-simple-restart-matching-and-nexus.md) 的最新补充；涉及参数和数据目录的匹配策略，以本轮明确的通用规则为准。

## 1. 本轮用户明确的规则

1. 采用通用识别器，覆盖不同业务应用及 Nexus、ZooKeeper、Kafka 等中间件。
2. 监听端口、应用目录、启动应用不变，即使 PID、JVM 参数、环境变量、数据目录等改变，也可以认为仍是原部署单元。
3. 后续支持人工调整部署单元。
4. 本轮先固化规则，不实施识别器代码。

据此修订上一轮建议：**数据目录、配置参数等普通启动参数的变化，不再单独阻止自动延续，也不触发新建单元。** 应用目录、启动目标、监听仍是核心条件。

## 2. 核心匹配规则

```text
在同一来源资产、同一已确定环境中：
  application_directory 相同
  launch_target 相同
  listening_ports 匹配
  且唯一对应已有实例、无已知身份/隔离范围冲突
    => 沿用 instance ID
    => 沿既有 instance → unit 绑定沿用 unit ID
    => 更新参数、PID 等观察，保留变化历史
```

资产优先使用来源实例 + JumpServer asset ID，不只使用 IP。已知隔离范围作为范围约束，未知就保留 UNKNOWN；不假定未知范围就是宿主机命名空间。不同环境、不同机器不因三个核心字段相同而自动合并。

这是平台采用的服务连续性启发式策略，自动结果为 INFERRED，保存依据和规则版本；平台 ID 独立生成，不以特征哈希替代。已有 DevOps 应用/原生资源等明确绑定及人工调整优先于弱自动匹配。

通用识别器首先解决“本地观察是否对应已创建实例”，再找回单元。首次跨机器、跨环境的服务是否属于同一个逻辑单元，仍通过已有来源绑定或人工归组；不能把这个本地指纹当成全公司单元唯一键。

## 3. 身份特征和变化属性分开

| 项目 | 是否进入通用核心匹配 | 说明 |
|---|---|---|
| 来源实例、资产、环境 | 是，限定范围 | 不跨机器/环境无条件归并 |
| 应用目录 | 是 | 程序/部署所在目录，不使用数据目录替代 |
| 启动目标 | 是 | 业务 jar、主类、脚本或原生程序入口 |
| 实际监听端口 | 是 | 来自已有监听采集，缺失不等于相同 |
| 已知隔离范围、协议 | 一致性约束 | 有证据时检查，不补未知值 |
| PID、PPID、启动时间、运行时长 | 否 | 本次运行属性 |
| JVM 内存、GC、诊断参数 | 否 | 变化更新观察 |
| 环境变量 | 否 | 变化不单独决定身份；未采集则不能宣称已知 |
| 数据目录、日志目录、临时目录 | 否 | 与应用目录分开，允许变化 |
| 配置文件路径、普通业务参数 | 否，除非是提取目录/入口的明确来源 | 核心字段相同时允许参数变化 |
| 领域、系统、管理名称 | 否 | 平台管理信息，人工维护 |
| 软件产品标签 | 否 | 可帮助展示，不能要求先识别成某个已知产品才能匹配 |

“启动目标/目录可以从参数提取”与“不比较全部参数”是两回事。例如 `java -jar /apps/photo/server.jar` 中的 jar 路径定义了启动目标和程序目录；路径变化会反映在核心字段里。`--data-dir` 改变则只更新数据目录属性。

不因为一个未分类参数改变就一律停止匹配；只要核心条件满足且无已知冲突，就按本轮规则自动延续。这是对上一份文档中“未知参数变化默认待核验”的进一步简化。

## 4. 通用架构：启动形式提取，统一规则匹配

```text
已有快照/命令/监听观察
  → 解析启动形式与特征
  → 统一特征描述
  → 查询人工绑定及已有来源绑定
  → 通用匹配器
  → MATCH / AMBIGUOUS / INSUFFICIENT_EVIDENCE / NEW_CANDIDATE
  → 保存观察和匹配依据
```

按启动形式提供可复用的提取能力：

| 启动形式 | 启动目标 | 应用目录提取思路 |
|---|---|---|
| Java `-jar` | 业务 jar 路径/名称 | 绝对 jar 路径的父目录 |
| Java 主类 / classpath | 主类及可识别的业务启动入口 | 明确启动路径、应用 base 参数，或唯一合理的代码路径候选 |
| 包装启动器 | 能从通用启动结构解出的目标；否则保留包装入口 | 启动脚本/模块路径等已有线索；不猜测真实业务目录 |
| Node / Python / Shell 脚本 | 实际脚本入口 | 已知绝对脚本路径的父目录 |
| 模块启动 | 已明确的模块名 | 有已知运行目录/部署路径才生成目录候选 |
| 原生程序 | 可执行程序入口 | 二进制所在目录或已有明确部署目录，标明来源 |
| 其他形式 | 可确认的实际入口 | 不能可靠提取时输出缺失项，不只凭名称猜目录 |

识别策略不依赖“这是 Nexus 还是 Kafka”的单独分支。以后某种通用启动结构提取不充分，可以扩展提取器；输出结构和匹配器保持一致。

例如 Java 通用包装入口本身可能过于通用，仍需结合应用目录、监听及已有绑定。不能得到完整核心特征时允许输出 INSUFFICIENT_EVIDENCE，通用不等于对每条命令都强行给出唯一结论。

## 5. 字段的统一定义

### 5.1 application_directory

表示程序部署/启动所在目录，不是数据、日志或缓存目录。

- 优先使用人工确认的目录规则或已有明确部署绑定。
- 否则从已有绝对程序、jar、脚本或启动器路径提取。
- Java 主类场景的 classpath 可能包含多个目录，只能产生有依据的候选；无法唯一判断则保留 UNKNOWN，不把 `/`、JDK 根目录或 `/conf` 随意当成应用目录。
- 原生程序的 `/usr/local/bin` 等可能是共享安装目录，可以保留为弱目录线索；它本身不证明唯一性。
- 路径只做可解释的词法规范化，保留大小写和原值；不访问宿主机文件，不假定远端符号链接已解析。
- 当前快照没有可靠 cwd 时，不将相对路径自动变成绝对路径。明确的人工规则可补充目录，但不伪装成采集事实。

### 5.2 launch_target

表示启动了哪个程序入口。例如：业务 jar、主类、启动脚本、原生可执行程序。

Java 的 JDK 可执行文件路径不是唯一的业务入口。主类、jar、脚本等应从可解释的启动结构提取；遇到包装器不能仅因出现一个类名就将任意业务参数当成真实入口。

默认不全局删除 jar 名称中的数字或版本。包升级导致入口/目录变化时，可以使用已保存别名或人工调整扩展；这与本轮“入口不变但参数变化”是不同情况。

### 5.3 listening_ports

- 使用进程 ports，或 appPorts 中通过 PID 对应的实际监听证据；声明端口、命令端口提示单独保存，不冒充实际监听。
- 默认比较去重、排序后的监听端口集合，避免顺序变化导致新候选。
- 有协议时检查协议兼容性，保留完整地址/端口/协议证据；未采集协议不补默认 TCP。
- 地址绑定等额外信息作为观察属性保留；同机多个进程可使用相同端口时，必须结合已有隔离范围和唯一候选检查，不能只取端口数字。
- 多端口服务可由人工指定参与匹配的服务端口集合；未指定时使用全部已观察监听。增加辅助监听造成集合变化时保留候选，不直接新建单元。
- 未采集监听、仅有旧声明、或无法关联 PID，均不能解释为“端口一致”。

端口提示可用于检索候选，证据补全后再决定自动延续；实际监听条件不足时不通过空值相等绕过规则。

## 6. 标准特征与可变观察

结构示意（不包含生产数据）：

```text
identity_features:
  source_instance_key
  asset_id
  environment
  known_isolation_scope
  application_directory
  launch_mode
  launch_target
  listening_ports
  evidence_quality
  extractor_version

observed_attributes:
  pid / ppid / started_at
  原命令的脱敏记录
  JVM/业务参数
  已获得的数据/配置/日志路径声明
  CPU/内存等运行观察
  观察时间与原始记录位置
```

候选检索可对范围、目录、目标、数字端口集合计算指纹，再进行协议、隔离范围、来源绑定和冲突检查。协议等未知值后来得到补全，不应仅因哈希变化就重新建对象；仍需查兼容候选。

环境变量的变化按用户策略不参与身份判断，但当前日快照不提供完整环境变量。因此只分析已有脱敏命令/快照能支持的内容，不额外读取 `/proc/.../environ` 或 Docker Env，不保存凭据。

## 7. 各类服务使用同一策略

| 场景 | 统一识别依据 | 参数变化如何处理 |
|---|---|---|
| Nexus | 已提取应用目录 + 启动入口 + 实际监听 | JVM、karaf.data、日志/临时目录变化仍延续 |
| ZooKeeper | 已提取程序目录 + 启动入口 + 实际监听 | 数据/配置路径等作为观察更新，不单独分裂单元 |
| Kafka | 已提取程序目录 + 启动入口 + 实际监听 | JVM、数据目录、普通启动参数变化仍延续 |
| 业务 Java Jar | jar 所在目录 + jar 启动目标 + 实际监听 | 内存、业务参数、数据目录变化仍延续 |
| Redis 等原生服务 | 程序目录/入口 + 实际监听 | 可获得的普通参数变化仍延续 |

这里没有从命令补默认端口，也没有声称现有每条记录已具备目录/监听。表中规则在核心字段可提取时适用；缺失项如实返回。

本轮明确接受参数变化可能带来的业务语义变化，自动结果保持 INFERRED，并允许后续人工调整。数据目录不再作为自动“是否同一部署”的否决条件。

## 8. 匹配结果和每日动作

| 结果 | 含义 | 动作 |
|---|---|---|
| MATCH | 唯一兼容命中，未违反人工规则或强来源绑定 | 沿用实例和单元，追加本次参数/运行观察 |
| AMBIGUOUS | 命中多个对象，或存在竞争观察/身份冲突 | 保留候选，不任取首项，不批量合并 |
| INSUFFICIENT_EVIDENCE | 目录、目标、实际监听或范围不足 | 保存缺失原因，沿用已知历史供展示，不宣称本次已确认 |
| NEW_CANDIDATE | 核心信息可用，但无兼容绑定 | 幂等保存候选；是否创建新单元由后续创建策略决定 |

同一批观察中，如果多个不能区分的进程共享全部核心特征，不先按指纹折叠成一条；应保留各进程证据并输出歧义。已登记的多进程服务可以按既有关系处理，不能默认一个 PID 必须对应一个单元。

参数变化既不创建新单元，也不重算已有 unit/instance ID。新候选重复出现时更新其观察，不每天生成重复候选。跨主机/环境的集群或业务归组不由此指纹自动完成。

失败/partial 检查不支持负向删除判断；来源缺失策略沿用 03 的完整性和按来源处理规则。

## 9. 人工调整是持久规则，不是一次性页面修改

需要支持：改名、分类、绑定到既有单元、合并重复的进程发现单元、拆分错误归组、调整实例归属及指定识别别名/服务端口。

建议优先级：

```text
有效的人工绑定/禁止归并规则
  → 已确认来源身份绑定
  → 通用自动匹配
  → 新候选或未解析结果
```

人工调整后持久保存：绑定来源 MANUAL、目标实例/单元、适用范围、锁定状态、有效期、特征别名、调整原因及审计记录。可以复用已设计的来源绑定、规则/别名和 catalog_change，不要求本轮再引入一套主数据模型。

- 同步不能把人工归属自动改回去。
- 人工明确拒绝的匹配，要保存禁止归并约束，避免下一次重新生成同样错误关联。
- 合并进程发现单元时保留旧 ID 的可追溯映射，并更新后续匹配绑定，避免旧对象再次被创建。
- 合并涉及不同 DevOps app ID 时需遵守“一应用一单元、单元最多一个主要应用”的既定约束，不能静默变成多个应用共用一个单元。
- 实例归属调整不能顺带猜测或改变其环境；目标单元有相同环境关联后再更新引用。
- 当前绑定改变须记录前后关系，旧快照和旧观察不重写。历史查看区分当时识别结果与当前管理归属。

自动匹配后，未来扫描仍应用人工规则的适用范围；人工调整不成为跨资产、跨环境无限复用的绑定。

## 10. 第一期验收场景

后续进入实现时，用小型脱敏 fixture 验证：

1. 同资产/环境、目录/入口/监听相同，PID 或 JVM 参数变化：MATCH，DU/DI 不变。
2. 上述条件相同，数据目录、配置参数变化：MATCH，保存属性差异。
3. 无实际环境变量数据：不读取或编造环境变量，也不以缺失阻止已有核心匹配。
4. Nexus、ZooKeeper、Kafka、未知业务主类都进入统一匹配器，不要求先有产品专属规则。
5. 入口/目录或参与匹配的端口改变：先查别名与兼容候选，不直接重复创建。
6. 多进程同特征、隔离范围冲突、强来源 ID 冲突：保留歧义，不取首项。
7. 目录/监听未采集与真实空集合区分；UNKNOWN 不因相等而视为有效证据。
8. 人工合并、拆分、改归属后再次同步：人工结果保留，旧 ID 可追溯，不重建重复单元。
9. 相同特征在不同主机/环境出现：不自动全局合并，集群归组另行处理。
10. 重复导入、旧版晚到、失败采集和参数微调，不造成删除重建或当前状态回滚。

## 11. 本轮结论

采用“统一启动特征 + 通用匹配器 + 人工纠正优先”的第一期方向，不按具体软件分别定义单元身份。

同一资产/环境内，应用目录、启动目标和实际监听一致且唯一兼容命中，即使 PID、JVM、环境变量、数据目录等变化，也自动沿用已有实例与单元。参数变化只更新观察；多候选和证据不足如实保留。

本次仅固化规则并更新分析索引，未编写识别器代码、执行建表或修改采集流程。
