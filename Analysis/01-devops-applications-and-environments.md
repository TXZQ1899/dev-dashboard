# 01：DevOps 应用列表与环境部署数据分析

日期：2026-10-21。状态：现状分析与初步结论，待业务讨论。

本轮只分析现有数据，不修改采集器、snapshot 定义、展示逻辑或数据库设计。未读取生产全量快照，也未计算当前实际应用数量。

## 1. 用户已明确的业务事实

1. 采集流程维持现状，继续将 JSON 快照写入本地数据卷。
2. 应用列表的成员会变化；清理无效流水线后，应用数量可能减少。
3. 应用名称、Git 地址、应用 ID、应用类型、仓库分类一般不变，可先视为相对稳定的信息。
4. 应用在测试、仿真、生产环境中的部署情况会变化，包括 IP、规格、发布时间、Git 分支、发布状态、部署 ID、配置 ID，以及说明中的进程信息等。
5. 各类数据分别讨论，先分析现状，再进入设计；每次分析保存在 `Analysis` 目录。

“361 → 351”作为用户给出的数量变化场景，不作为本次实测统计。

## 2. 当前数据实际包含哪些对象

当前 `snapshot.json` 的结构是：

```text
一份 DevOps 采集快照
  ├─ collectedAt / source / scope / complete
  └─ apps[]：本次观察到的应用清单
       ├─ 应用 ID、名称、类型、默认仓库等
       ├─ capturedAt
       └─ envs
            ├─ TEST[]
            ├─ SIMULATION[]
            └─ PRODUCT[]
                 └─ IP、部署 ID、配置 ID、分支、发布状态、步骤等
```

有三个不同观察层次：

- **清单层**：这次看到了哪些应用，和上次相比有哪些新增、哪些不再出现。
- **应用层**：同一应用 ID 对应的名称、默认仓库、类型等属性。
- **环境部署层**：同一应用在某个环境下的部署记录集合及每条记录的状态。

页面还将 ECS、服务器规格、JumpServer 进程与目录信息关联进来。因而“应用页面上的字段”不全是 `snapshot.json` 中的字段。

DevOps 清单中的一个应用是被管理的应用/流水线配置对象，不是一条流水线执行记录；环境部署记录也不是完整的发布事件历史。

## 3. 应用清单：属性相对稳定，成员集合会变化

应用数是 `apps[]` 的统计结果，不是永久固定的属性。需要分别观察：

| 比较对象 | 可观察到的变化 | 能得出的结论 |
|---|---|---|
| 本次和上次的应用 ID 集合 | 新增 ID、不再出现的 ID、持续出现的 ID | 清单成员发生变化 |
| 持续出现的相同 ID | 名称、仓库等字段改变 | 同一来源应用的属性变化候选 |
| 相同名称、不同 ID | 原 ID 消失，新 ID 出现 | 不能只按名称视为同一对象，可能是删除重建 |
| 数量从 361 变成 351 | 净减少 10 | 数量本身不能列出具体移除项；也可能同时有新增和移除 |

在用户明确确认“清理无效流水线”的场景中，清单减少可以有业务解释。但仅凭两份快照不应给每个缺失 ID 自动附加“确定删除”的原因或精确删除时间。

当前 `fetch_apps()` 会校验分页总数、重复 ID 及采集期间总数是否变化；应用采集失败会阻止生成该次成功全量结果。这提供了完整性检查，但 `scope=all` 仍应结合实际来源实例、账号可见范围理解，不等于拥有系统删除事件审计。

## 4. 应用层字段：稳定标识与相对稳定属性

下表的变化频率判断以用户描述为主；本轮未对历史文件做实测频率统计。

| 页面/业务概念 | 当前字段或计算 | 变化特点 | 分析结论 |
|---|---|---|---|
| 应用 ID | `apps[].id` | 同一来源对象的稳定标识 | 用于识别同一来源内持续存在的应用；删除重建不能按名称自动合并；是否复用旧 ID 尚无契约 |
| 应用名称 | `apps[].name` | 相对稳定 | 更名不必然代表创建了新应用 |
| 应用类型 | `apps[].appType` | 相对稳定 | 当前代码已采集；旧快照可能没有，缺失不能当作类型变更 |
| 默认 Git 地址 | `apps[].repository` | 相对稳定 | 迁库、地址规范化或维护配置仍可能使其变化；与环境覆盖地址分别理解 |
| 仓库分类 | `repositoryCategory(app.repository)` | 通常随默认仓库地址保持稳定 | 是展示规则的计算结果，不是当前 app JSON 中独立采集的分类字段 |
| HTTP 名称/路径 | `apps[].http` | 相对稳定的配置 | 可以调整；不是永不变化的标识 |
| 应用声明端口 | `apps[].port` | 可变配置 | 当前来源是应用配置的 HTTP 端口，不证明进程实际监听 |
| 应用默认分支 | `apps[].branch` | 可变配置 | 与具体环境记录中的分支有区别；不等于所有部署正在运行该分支 |
| 应用采集时间 | `apps[].capturedAt` | 每次采集可能变化 | 采集元信息，不能据此认为应用业务配置变化 |

当前页面“仓库分类”根据 Git 地址的主机名计算，例如映射为 Local Gitlab、阿里云效、其他、未提供等。它与采集导出中的“代码库类型”不是同一个字段：`export_devops.py` 能从 `defaultContrVersionType` 生成 CSV 的“代码库类型”，而当前 `collect_application()` 的 app JSON 没有保存该字段。此次只说明现状，不补字段。

因此，用户所说“一般不变”可以归为相对稳定属性，但只有应用 ID 承担当前来源对象身份；名称、Git 地址、类型、分类不能全部当成不可修改的身份键。

## 5. 环境部署层：集合与记录内容都可能变化

`TEST / SIMULATION / PRODUCT` 是当前约定的三个环境代码；变化主要发生在某个应用是否有该环境配置、该环境中有哪些部署记录，以及记录内容。

```text
同一个应用
  昨天：TEST -> IP-A
  今天：TEST -> IP-B、IP-C

应用本身可以没有变化，测试环境的部署成员和数量已经变化。
```

一个环境下是数组，不能假定“一个应用 × 一个环境只对应一台服务器”。同一 IP 也可能有多条部署记录，不应只按 IP 合并。

| 概念 | 当前字段 | 变化特点与现状 |
|---|---|---|
| 部署服务器 | `envs[env][].ip` | 可变化；迁移、扩缩容、调整部署目标等均可能改变记录集合 |
| 部署 ID | `.deploy` | 可以随部署对象调整而变化；没有证据证明它每次发布都变化，或跨应用/环境全局唯一 |
| 配置 ID | `.config` | 可以变化；更换 ID 与原配置内容修改是不同情形，快照不包含配置 ID 对应的全部内容 |
| 环境仓库地址 | `.repository` | 可覆盖应用默认仓库；测试配置可返回自己的仓库地址 |
| 环境分支 | `.branch` | 可变化，但当前值可能来自配置，也可能是约定推断，必须结合 `.branchSource` |
| 端口 | `.port` | 当前采集器直接复制应用声明端口；虽放在部署记录里，也未单独从目标进程核验 |
| 最近发布时间 | `.lastPublishedAt` | 随被观察到的步骤时间变化；没有历史记录时可能为空，不能用采集时间补齐 |
| 发布状态 | `.publishStatus` | 可变化；包含成功、失败说明、无运行记录等，须与读取状态区分 |
| 时间来源说明 | `.publishTimeSource` | 记录使用 PushIn endTime 还是 startTime 等依据；不是发布事件本身 |
| 读取状态 | `.status` | 当前表示采集/记录情况，如成功、无环境配置、无部署实例、实例未返回 IP |
| 错误说明 | `.error` | 用于采集错误/说明；当前采集路径初始化为空，重要请求异常通常中断成功全量结果 |
| 步骤信息 | `.pushIn[]` | 可变化；正常保存 PushIn，缺少有效 PushIn 时间时也可能保存其他失败步骤 |

两个需要明确区分的来源规则：

- **测试环境**：有配置 ID 时，分支读取配置的 `versionControlName`，仓库读取 `versionControlUrl` 或回退应用默认地址。
- **仿真/生产环境**：当前采集代码按约定写入 `master`，`branchSource` 明确说明来源。这个值不是对服务器当前代码分支的实时核验。

另外，读取状态为“成功”目前主要由部署记录是否返回 IP 决定，不能据此推出发布成功、进程存活或服务健康。

## 6. 规格、进程说明等：应用页面关联出来的数据

| 页面字段 | 实际来源 | 为什么可能变化 | 不能直接推导什么 |
|---|---|---|---|
| CPU/内存规格 | `server-specs.json` 或 `ecs-snapshot.json`，通过部署 IP 查找 | 同一主机升降配、目标主机更换、来源补采或缺失 | 规格变化不一定表示应用配置或部署对象变化 |
| 说明中的 PID | JumpServer `inspection.processes[]`，经应用匹配 | 进程重启、目标变化、不同进程被匹配、检查结果变化 | PID 不是应用永久标识，也不是部署 ID |
| 说明中的进程名称 | 原进程名称/命令解析出的 jar 或 Tomcat 业务名称 | 启动方式、包名、目录或匹配结果变化 | 展示业务名称不一定等于原始进程 `name` |
| 说明中的端口 | 优先 appPorts 按 PID 关联；其次命令解析；最后回退声明端口 | 实际监听、启动参数或回退路径变化 | 展示出端口不一定意味着本轮实际观察到监听 |
| 说明中的部署目录 | JumpServer `inspection.webapps`，名称匹配 | 部署目录和采集/匹配结果变化 | 目录存在不代表进程正在运行 |
| 服务器收录/登录/进程匹配提示 | JumpServer 与规格快照及页面判断 | 可见范围、登录结果、检查覆盖、运行状态变化 | 未登录/未采集不能等同于进程不存在 |

当前 `ipSpecSummary()` 优先使用可用的 server-specs，再回退 ECS 规格；server-specs 内存还会换算成标称规格。因此页面中的“2C 4G”是关联与格式化结果，不是 DevOps 原始字段。

当前应用进程匹配采用名称、jar、命令行等规则，`matchAppToProcess()` 返回首先匹配的进程。页面说明没有完整枚举/表达所有可能候选，因此“显示了一个 PID”不能自动解释为已证明唯一的应用进程归属。本轮只记录该现状，不修改匹配规则。

结论：即使 DevOps 的 app JSON 完全未变，规格和进程说明仍可能因其他快照更新或展示规则变化而改变。不能将这些展示变化全部归为“DevOps 应用数据变化”。

## 7. 当前页面中几个时间与状态口径

| 位置 | 当前代码使用的数据 | 语义 |
|---|---|---|
| 环境展开明细“最后发布时间（Push In）” | `r.lastPublishedAt` | DevOps 运行步骤中观察到的时间；需结合状态、操作类型和时间来源 |
| 应用主列表“最近成功 Push In”及对应 CSV | `latestAppDeploymentTime()` | 应用匹配进程的 startedAt 与 webapps mtime 中的最新时间，不直接读取 DevOps PushIn 时间 |
| 环境明细“发布状态” | 通常为 `r.publishStatus`；满足页面条件时显示“超过一年未部署” | 页面可能使用进程/目录时间和缺失情况生成标签，不等于源 publishStatus 被修改 |
| 整批采集时间 | 根 `collectedAt` | 该批采集元信息，不是所有应用的发布时间 |
| 应用采集时间 | `capturedAt` | 构建应用采集对象时写入，各环境随后分次请求；不代表所有请求严格同一时刻 |
| 进程检查时间/进程启动时间 | `inspection.checkedAt` / `process.startedAt` | 分别表示检查时刻与已观察进程的启动时间 |

进程重启可能没有重新发布代码，目录 mtime 也可能因文件维护改变。主列表名称与计算依据之间存在上述语义差异，需要讨论业务期望后再决定是否调整，不能先把三种时间当成同一个字段。

当没有匹配到有效进程/目录时间时，当前“超过一年未部署”判断也可能成立。因此它包含“缺少可用观察”的情形，单靠这个标签不能证明已经一年没有发布。

## 8. 空值、未配置与缺失分别是什么意思

| 现象 | 当前可解释范围 |
|---|---|
| 应用 ID 未出现在下一份清单中 | 下一次该来源/范围的清单不再观察到；用户确认清理时可补充业务原因 |
| `status=无环境配置` | 采集接口被识别为没有对应环境配置；与请求失败不同 |
| `status=无部署实例` | 环境响应有部署列表但为空；不能与无环境配置合并 |
| `status=实例未返回IP` | 有部署条目但缺少 IP，不能虚构部署目标 |
| 环境数组为空或旧字段缺失 | 需结合格式及来源解释；当前页面可能显示待核实，不能机械解释为零部署 |
| `lastPublishedAt` 为空 | 没有可用发布步骤时间，不表示从未发布 |
| 规格为空、说明无 PID | 未采集、未关联、匹配失败或实际缺失都有可能；需要看其他来源状态 |

缺失是分析结果的一部分，不应为了方便“静态/动态分类”而全部变成空字符串或零。

## 9. 本轮分析结论

1. **应用列表作为集合是动态的，应用基础属性通常相对稳定。** 两者并不矛盾；应用减少与仍存在应用的属性不变可以同时发生。
2. **应用 ID 属于身份标识，名称、Git 地址、类型属于相对稳定属性。** 仓库分类则是当前规则对 Git 地址的计算结果。
3. **应用的环境部署是可变化的多条记录集合。** 环境是否配置、目标数量与每条记录内容都需要分别讨论。
4. **部署 ID、配置 ID、PID 的生命周期不同。** 不能把它们当作同一个对象的几种叫法，也不能假定每次发布都会产生新 ID。
5. **声明端口、命令行端口、实际监听端口不是同一种证据。** 当前同一页面已存在这些不同来源的值，需要在分析中保留区别。
6. **规格与进程说明属于其他来源补充或关联结果。** 它们可以变化而 DevOps 快照不变，变化也可能源于匹配规则或采集可用性。
7. **DevOps 发布步骤时间、进程启动时间、目录修改时间必须分别理解。** 当前页面存在混用名称的现状，应先澄清业务含义。
8. **采集元信息变化不等于业务变化，值没变化也不等于本次没有重新观察。** 本轮只建立区分，不据此确定版本存储方式。

初步分类如下，供后续讨论：

| 类别 | 本轮归入的数据 |
|---|---|
| 稳定标识 | 同一 DevOps 来源内的应用 ID |
| 相对稳定属性 | 应用名称、默认 Git 地址、应用类型、HTTP 名称等 |
| 成员集合变化 | 应用清单、应用的环境配置及环境部署记录集合 |
| 部署配置/步骤状态变化 | IP、部署 ID、配置 ID、环境仓库/分支、声明端口、发布步骤与状态 |
| 运行观察变化 | PID、进程启动时间、实际监听、登录与检查结果等，来自关联来源 |
| 来源补充及展示计算 | 规格摘要、仓库分类、进程业务名、说明文本、时间汇总及标签 |
| 采集元信息变化 | collectedAt、capturedAt、source、scope、complete 等；其中 scope/complete 还决定比较是否可信 |

## 10. 后续讨论项

以下问题尚未定稿，本轮不预设答案：

1. **应用生命周期口径**：清理的流水线在管理视角中是“已删除”“已停用”还是保留为历史对象？哪些情况能够确认原因？
2. **相对稳定属性的边界**：名称、默认仓库、类型变更时，业务上是否仍认为同一个应用？当前先按同源 app ID 理解。
3. **部署 ID / 配置 ID 的业务含义**：它们分别在重发、扩缩容、换机、删除重建时如何变化？仅凭字段名和快照尚不能确认。
4. **页面“发布时间”的期望口径**：希望表达 DevOps 发布完成、进程启动，还是部署目录变化？需要先确认不同指标的用途。
5. **规格和进程信息的归属**：是应用本身属性，还是某次部署目标/检查的补充信息？当前源码支持后者，具体管理表达待讨论。

这些问题形成共识后，再讨论该类型数据如何落库、如何保留变化；其他数据类型继续按同样步骤单独分析。
