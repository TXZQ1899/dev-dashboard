# 应用快照生成部署目录：第一期实现

## 范围与结论

本期根据用户后续的实施要求，实现已有 DevOps 应用列表 → 部署单元、环境记录及部署实例，并在应用列表增加「部署单元」Tab。采用 MySQL 8.4，与快照目录并行持久化。采集器、原始 snapshot 字段及原有版本切换机制保持不变。

业务领域、业务系统只建表，不生成推测的领域或系统。部署单元的系统归属可为空。中间件没有应用 ID 的情况通过通用来源关联表预留，当前不从进程、数据库或中间件创建对象；05 的通用进程识别器尚未实施。

## 对象与来源

| 管理对象 | 本期生成规则 | 身份与来源 |
|---|---|---|
| 业务领域 | 空表，后续维护 | 平台 UUID |
| 业务系统 | 空表，后续维护，归属一个领域 | 平台 UUID |
| 部署单元 | 每个有效应用 ID 一个单元，类型 APPLICATION | 平台 UUID；来源实例 + DEVOPS_APPLICATION + 应用 ID 唯一绑定 |
| 单元环境 | 每个单元保留 TEST、SIMULATION、PRODUCT 三条关联 | 单元 + 环境唯一；区分无配置、配置为空、有记录、未知 |
| 部署实例 | 有可解析 IP 的真实部署记录创建 HOST_DEPLOYMENT | 平台 UUID；在单元和环境内匹配来源成员；同 IP 可有多个实例 |

单元主表没有必填应用 ID。应用 ID 在 `deployment_unit_source.native_key_json` 内，不阻止未来无应用 ID 的 DATABASE、MIDDLEWARE、OTHER 单元存在。技术类型、服务地址、网络范围、协议和主机引用预留为空，不凭本期数据补造。

`business_system.domain_id` 必填，`deployment_unit.system_id` 可空。将来通过系统获得领域归属，避免同一个单元上的领域和系统互相矛盾。

## 环境与实例创建

- 「无环境配置」生成环境关联，不生成实例。
- 「无部署实例」生成配置为空的环境关联，不生成实例。
- 缺字段、空数组不能证明环境不存在，记录为 UNKNOWN。
- 缺 IP、IP 非法、同一 deploy/IP/端口却内容冲突的记录保存在待解析观察中，不生成占位实例。
- 完全相同的重复部署记录去重；同 IP、不同部署成员或端口仍分别保留。
- 端口优先使用部署记录显式字段；字段不存在时才沿用应用声明端口。显式空值不会被覆盖。两者都不是实测监听端口。
- 不用 IP 自动关联 ECS/JumpServer，不推断主机规格、环境、运行状态或协议。

## 每日更新与身份连续性

独立导入线程每 30 秒检查当前 ready 版本，不调用采集器。已存在相同来源、快照 SHA-256、映射规则版本的成功批次时直接返回。其他来源独立同步复制同一份应用快照，不会重复生成目录版本。页面也可手动触发读取当前快照。

单元按来源应用 ID 匹配，UUID 保持不变。名称默认跟随来源；未来将 `name_policy` 改为 MANUAL 后不覆盖人工名称。系统归属、说明和管理状态不被采集覆盖。

实例只在所属单元及同一环境内匹配，优先顺序为：

1. 已绑定的 deploy + IP + 声明端口完全相同。
2. 同一 deploy 下唯一 IP 匹配，且本批该 IP 只有一个成员，允许端口变化。
3. 本批同一 deploy 只有一个成员，历史绑定也只指向一个实例，允许 IP/端口变化。
4. 缺少连续性证据时新建；多个旧实例可能匹配时保留待解析，不任选一个旧实例。

deploy 不能被假定为全球唯一实例 ID，故实例身份连续性标为 INFERRED，保留匹配依据和历史来源别名；来源应用 ID 的直接绑定为 EXACT。多成员部署缩为一个新地址且旧成员身份不唯一时，保留 AMBIGUOUS。此规则不用于识别进程重启。

## 缺失、失败与历史

只有根对象明确 `complete=true` 且 `scope=all`，才把本批缺失应用标为 NOT_OBSERVED；不删除单元及其管理属性。旧格式缺少完整性标志时只添加/更新正向观察。

环境只有明确返回记录、无未解析问题且状态完整，才把本批缺失实例标为 NOT_OBSERVED。不完整环境保留旧实例，页面显示观察范围待核实；这不代表已确认旧实例仍在线。空数组不触发移除。

每个新批次保存来源版本路径、SHA-256、采集时间、映射规则版本、完整性、逐对象观察和变更。采集时间与导入时间分开；发布时刻直接保留 Push In 来源字段，不把相邻快照变化称为真实发布事件。

业务导入在单个事务内完成，成功才切换当前批次；校验失败、写入失败、期间当前快照切换则回滚。迁移在导入前单独执行并保存校验和。最近任务结果保存于数据卷 `catalog-job.json`；失败批次没有半成品业务记录。

当前目录保留较新的管理对象和观察；切换应用页面到更旧快照不会回滚目录或人工信息。页面显示来源时间与版本不一致说明。本期不提供按历史日期查询完整目录视图或回滚管理数据。

## 实现位置与运行

- `environment-web/runtime/migrations/001_deployment_catalog.sql`：四类管理对象及环境、来源、导入、观察、审计表。
- `environment-web/runtime/deployment_catalog.py`：纯快照归一化、迁移、事务导入、目录查询。
- `environment-web/runtime/service.py`：独立自动导入线程与同源 API。
- `environment-web/app/applications/deployment-units.tsx`：列表、搜索、分页、历史来源开关、环境实例展开。
- `environment-web/compose.yaml`：MySQL 服务和 `envscope-mysql` 持久卷；应用镜像内包含 Python MySQL 驱动。

验证使用小型脱敏数据，覆盖 0/1/N 实例、同 IP 多成员、重复导入、连续更新、完整/不完整缺失、冲突、并发、旧版本保护和事务回滚。具体运行命令和持久化说明见 `environment-web/SETTINGS.md`。

## 本次验证结果（2026-10-21）

- 最终测试镜像 `envscope:catalog-test` 构建通过；应用以默认 node 用户首次空卷启动通过。首次验证发现 `/app` 根目录不可写，已在 Dockerfile 修正目录所有者。
- 容器内 Python 测试 83 项通过，其中包含 7 项真实 MySQL 8.4 集成测试；测试库与业务数据卷隔离。
- 应用库存与目录前端测试 14 项通过；新增前端文件 oxlint 通过。
- TypeScript 源码检查通过（排除现有 `.next` 目录）；默认 `tsc` 的既有 `.next/types` 生成文件问题本期未修改。
- 独立应用容器通过真实 HTTP 验证：使用镜像内现有快照自动创建 545 个单元、1473 个部署成员；目录来源哈希与当前快照一致；Tab 页面返回成功，实例查询及手动更新返回正常。1473 是部署成员数，不是去重服务器数，也不表示实测在线进程数。
- HTTP 验证未替代完整浏览器点击及视觉验收；测试容器和测试数据库在验收后清理，未更新现有业务容器或挂载其数据卷。

## 后续界面调整

按用户反馈，实例展开表格去掉「实例 ID」「来源观察」「最后观察时间」三列，保留 IP、声明端口、Git 分支、部署/配置 ID、发布时间和发布状态。底层身份、来源证据与时间记录继续保留；后台每 30 秒消费当前已完成快照的更新机制保持不变。
